# Muzia Evaluator ルーブリック

## 目的

Generatorの実装を、機能仕様、リポジトリのアーキテクチャ、テスト計画、
実行中のデスクトップアプリで観測できる動作に基づいて評価する。

Evaluatorは、Generatorの自信や作業ログではなく成果物を判定する。
見た目がもっともらしいUIだけでは、機能が動作している証拠として不十分である。

## 評価手順

1. 対象機能の`spec.md`と`tasks.md`を読む。
2. `docs/requirements.md`の関連要件を読む。
3. `docs/architecture.md`と`docs/testing.md`の関連ルールを読む。
4. 実装とテストを確認する。
5. 必須の自動チェックを実行する。
6. UI、画面遷移、ファイルスキャン、再生、永続化、プラットフォーム動作に
   影響する変更では、アプリを起動して操作する。
7. 以下の各評価基準を判定し、具体的な証拠を記録する。
8. 必須の評価基準がすべて合格した場合だけ`PASS`を返す。

動作を直接観測できる場合、実装の存在だけから動作成功を推測しない。
証拠には、実行中のアプリ、テスト結果、または対象箇所を特定できるコード参照を優先する。

## 評価基準

### 1. 要件適合性

対象機能の仕様書と参照先の製品要件にある、すべての受け入れ条件を満たしている。

合格条件:

- すべての受け入れ条件に証拠がある。
- 初期UIだけでなく、ユーザーフロー全体が動作する。
- 必要なローディング、空状態、エラー状態が処理されている。
- 必須の動作がスタブ、プレースホルダー、誤解を招く成功状態に置き換えられていない。

不合格条件:

- 必須の動作が不足している、または一部しか実装されていない。
- 仕様と矛盾する前提に依存している。
- エラーが握りつぶされている、または失敗が成功として表示される。

### 2. アーキテクチャと責務境界

`docs/architecture.md`に従い、MVVMのレイヤー境界を維持している。

合格条件:

- Widgetがファイルシステム、データベース、音声ライブラリへ直接アクセスしない。
- ViewModelがアプリケーション操作にRepositoryとServiceを使用する。
- プラットフォーム固有の動作がServiceまたは抽象化層に隔離されている。
- DomainモデルがFlutter UIやストレージ実装に依存しない。

不合格条件:

- レイヤー境界に違反している。
- 新しい外部依存が適切なServiceまたはRepositoryの背後に隔離されていない。
- 要件のない無関係なリファクタリングによって変更範囲が拡大している。

### 3. 検証とリグレッション対策

変更された動作を検証するテストが実装を支えている。

該当する場合、以下を実行する。

```bash
flutter analyze
flutter test
```

UI、ファイルスキャン、再生、永続化、デスクトップ動作に関する変更では、
対象プラットフォームのIntegration Testも実行する。

```bash
flutter test integration_test -d macos
flutter test integration_test -d windows
```

合格条件:

- 必須コマンドが成功する。
- テストが関連する成功、空、エラーの経路を対象にしている。
- テストがユーザーの実際の音楽ライブラリではなく、一時データやFakeを使用する。
- 既存テストの弱体化や削除によってリグレッションが隠されていない。

不合格条件:

- 必須チェックが失敗した、または実行されていない。
- 必須のIntegration Testを実行できないのに、その制限が報告されていない。
- 変更された動作を検証せずにテストだけが成功している。

### 4. ファイルの安全性

要件が明示的に許可していない限り、ユーザーの元の音楽ファイルを保持する。

合格条件:

- 元の音楽ファイルを削除、移動、上書き、変更しない。
- MVPのメタデータ編集がアプリケーションのライブラリ情報だけを変更する。
- ファイルパスと操作内容が実行前に検証される。
- 破壊的なライブラリ操作で、ライブラリからの削除とファイル削除が明確に区別される。

不合格条件:

- 元のファイルが意図せず変更される。
- ユーザーの明示的な指示なしにファイル操作が実行される。
- 破壊的な操作に確認または安全なエラー処理がない。

### 5. ユーザーに見える動作

実行中のmacOSまたはWindowsアプリが、対象フローについて仕様どおりに動作する。

合格条件:

- 主要なユーザーフローを、推測せずに完了できる。
- ローディング、成功、空、エラーの状態が表示される。
- ユーザー向けエラーが問題を説明し、不要な内部情報を露出しない。
- 該当する場合、デスクトップウィンドウのリサイズ後も操作できる。

不合格条件:

- 操作できそうに見えるコントロールが、示された動作を実行しない。
- 想定されるエラー経路でアプリがクラッシュする、または操作不能になる。
- 実行中アプリの確認が必要なのに、静的なコード確認だけで判定している。

## 判定ルール

いずれかの評価基準が不合格の場合、対象スプリントは失敗とする。
Generatorには、不合格になった基準、証拠、再試行に必要な具体的な最小修正を渡す。

必須の評価基準が不合格の場合、平均点を理由に承認してはならない。

## 評価結果の形式

以下の形式で結果を返す。

```md
# Evaluation

判定: PASS | FAIL

## 要件適合性

- 判定: PASS | FAIL
- 根拠:

## アーキテクチャと責務境界

- 判定: PASS | FAIL
- 根拠:

## 検証とリグレッション対策

- 判定: PASS | FAIL
- 根拠:

## ファイルの安全性

- 判定: PASS | FAIL
- 根拠:

## ユーザーに見える動作

- 判定: PASS | FAIL
- 根拠:

## 必須修正

-
```

すべての`FAIL`には観測可能な証拠を含める。点数や一般的な批評だけを返してはならない。
