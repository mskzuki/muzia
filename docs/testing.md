# Muzia テスト計画書

## 1. 目的

Muziaの機能が要件どおりに動作し、macOS / Windowsの両方でユーザーの音楽ファイルを安全に扱えることを検証する。

特に以下を重視する。

- ライブラリ情報の正確性
- ファイルを意図せず削除・移動・上書きしないこと
- 再スキャン時にユーザー編集を保持すること
- 大量ファイル処理中もUIを操作できること
- macOS / Windows間の挙動差を把握すること

## 2. テスト方針

Flutter標準のテスト機能を基本とし、テスト対象に応じて以下を使い分ける。

```text
単体テスト
  ↓ ロジック・状態遷移
Widgetテスト
  ↓ 画面・Widgetの表示と操作
Integration Test
  ↓ 実デスクトップアプリの主要フロー
```

テストは、可能な限り高速で不安定要因の少ない下位レイヤーに多く配置する。

## 3. 完了条件

実装または修正後、変更内容に応じて以下を実行する。

```bash
flutter analyze
flutter test
```

UI、画面遷移、ファイルスキャン、再生、永続化に影響する変更では、対象プラットフォームのIntegration Testも実行する。

macOS:

```bash
flutter test integration_test -d macos
```

Windows:

```bash
flutter test integration_test -d windows
```

以下の場合は、変更を完了扱いにしない。

- 静的解析に失敗している
- 関連するテストに失敗している
- 必須の動作確認を実行していない
- テストを実行できなかった理由を報告していない

## 4. テスト環境

### 対象環境

| 環境 | 用途 | 必須 |
| --- | --- | --- |
| macOSデスクトップ | macOSの起動・UI・ファイルアクセス・再生確認 | 必須 |
| Windowsデスクトップ | Windowsの起動・UI・ファイルアクセス・再生確認 | 必須 |
| Dart / Flutterテスト環境 | 単体・Widgetテスト | 必須 |

WindowsのIntegration TestはWindows環境で実行する。macOS上でWindowsの実機動作を確認したことにしてはならない。

## 5. テストデータ

### 5.1 テスト用音源

テストでは、ユーザーの実際の音楽フォルダを使用しない。

テスト用音源は、用途とライセンスを明確にした小容量のファイルを用意する。

最低限、以下の状態を用意する。

- メタデータが設定されたファイル
- タイトルが空のファイル
- アーティストが空のファイル
- アルバムが空のファイル
- 再生できない、または壊れたファイル
- 異なる拡張子のファイル
- 対応外のファイル
- 同じメタデータを持つ複数のファイル

テスト用音源をリポジトリに含める場合は、ライセンスとファイルサイズを確認する。

### 5.2 一時ディレクトリ

- テストごとに一時ディレクトリを作成する
- テスト終了後に一時ファイルを削除する
- 固定のユーザーディレクトリや実際の音楽フォルダを使用しない
- テスト間でDBやファイルを共有しない
- OSごとのパス区切り文字をハードコードしない

### 5.3 テスト用DB

Repositoryのテストでは、DriftのインメモリDBまたはテスト専用DBを使用する。

- テスト開始時にスキーマを初期化する
- テスト終了時にDBを破棄する
- 開発環境やユーザー環境のDBをテストで使用しない
- マイグレーションテストでは、旧スキーマのDBを用意する

## 6. 単体テスト

単体テストでは、FlutterのWidgetや実OSに依存しないロジックを検証する。

### 6.1 対象

- 検索
- フィルタリング
- ソート
- アーティスト・アルバムのグルーピング
- 対応ファイル形式の判定
- パスの正規化
- メタデータの変換
- メタデータ編集・一括編集
- ライブラリからの削除状態
- ViewModelの状態遷移
- 再生状態の変換
- DBのRepository処理

### 6.2 必須ケース

- 空のライブラリを処理できる
- 大文字・小文字が異なる検索を処理できる
- 検索結果が0件の場合を処理できる
- メタデータが欠落している楽曲を処理できる
- 複数楽曲の一括編集を処理できる
- 一括編集の失敗時にロールバックできる
- 削除済み楽曲を通常の一覧から除外できる
- ユーザー編集済みメタデータを再スキャンで上書きしない
- 存在しないファイルを再生しようとした場合にエラーになる
- macOS / Windowsのパスを正しく扱える

## 7. Widgetテスト

Widgetテストでは、ViewModelから受け取った状態が正しく表示され、ユーザー操作がViewModelへ伝わることを検証する。

### 7.1 対象画面

- ライブラリ画面
- 楽曲一覧
- アーティスト一覧
- アルバム一覧
- 検索欄
- メタデータ編集フォーム
- 一括編集フォーム
- 削除確認ダイアログ
- プレイヤー
- ローディング表示
- 空状態表示
- エラー表示

### 7.2 必須ケース

- 楽曲一覧にタイトル、アーティスト、アルバムを表示できる
- 楽曲を選択できる
- 複数の楽曲を選択・選択解除できる
- 検索結果を表示できる
- 検索結果なしを表示できる
- ローディング状態を表示できる
- エラー状態と再試行操作を表示できる
- メタデータ編集の保存・キャンセルが動作する
- 削除確認ダイアログに対象楽曲数が表示される
- 元ファイルを削除しない説明が表示される
- 再生・一時停止ボタンが状態に応じて変化する

## 8. Integration Test

Integration Testでは、実際のmacOS / Windowsデスクトップアプリを起動し、主要なユーザーフローを検証する。

### 8.1 起動

- アプリを起動できる
- 初期状態を表示できる
- 保存済みのライブラリ情報を読み込める
- 読み込み中の表示が行われる

### 8.2 フォルダ登録・スキャン

- フォルダ登録操作を開始できる
- フォルダ選択ダイアログをキャンセルできる
- 登録したフォルダをスキャンできる
- 対応ファイルが一覧に表示される
- 非対応ファイルが一覧に表示されない
- メタデータが一覧に反映される
- フォルダ変更後に新しいフォルダの内容が表示される
- スキャンエラーが表示される

### 8.3 アーティスト・アルバム

- アーティスト一覧を表示できる
- アーティストを選択できる
- 選択したアーティストのアルバム一覧を表示できる
- アルバムを選択して楽曲を表示できる
- 削除済み楽曲が一覧に混ざらない

### 8.4 検索

- タイトルで検索できる
- アーティストで検索できる
- アルバムで検索できる
- 検索結果をクリアできる
- 検索結果がない状態を表示できる

### 8.5 再生

- 楽曲を選択して再生できる
- 再生中の楽曲情報を表示できる
- 一時停止できる
- 再生できないファイルのエラーを表示できる

### 8.6 メタデータ編集

- タイトルを変更できる
- アーティストを変更できる
- アルバムを変更できる
- リリース情報を変更できる
- 保存後に一覧・検索へ反映される
- キャンセル時に変更されない
- 元の音楽ファイルが変更されない

### 8.7 メタデータ一括編集

- 複数の楽曲を選択できる
- 選択中の楽曲数を確認できる
- 対象項目を一括変更できる
- 変更結果が全対象楽曲へ反映される
- 一括編集の失敗結果を表示できる

### 8.8 ライブラリからの削除

- 楽曲をライブラリから削除できる
- 削除前に確認できる
- 元の音楽ファイルが残る
- 一覧、検索、アーティスト、アルバムから除外される
- アプリ再起動後も削除状態が保持される

## 9. 永続化・再起動テスト

以下の状態がアプリ再起動後も保持されることを確認する。

- 登録フォルダ
- 検出された楽曲
- アプリ上で変更したメタデータ
- ライブラリから削除した楽曲の状態

再起動テストでは、アプリを終了した後にDBファイルが保存されていることを前提にせず、ユーザーから見た状態を検証する。

## 10. ファイル安全性テスト

テスト前後で、テスト用音楽ファイルについて以下を比較する。

- ファイルが存在すること
- ファイルパスが変わっていないこと
- ファイルサイズが変わっていないこと
- ファイル内容が変わっていないこと
- メタデータ書き戻しが発生していないこと

ライブラリからの削除テストでは、DB上からは除外されてもファイルが残っていることを必ず確認する。

## 11. プラットフォーム別確認

### macOS

- フォルダ選択ダイアログが開く
- ユーザーが選択したフォルダを読み込める
- Sandbox / Entitlement設定が動作する
- 日本語や特殊文字を含むパスを扱える
- 音声ファイルを再生できる
- Releaseビルドでも必要なファイルへアクセスできる

### Windows

- フォルダ選択ダイアログが開く
- ユーザーが選択したフォルダを読み込める
- ドライブレターを含むパスを扱える
- 日本語や特殊文字を含むパスを扱える
- 音声ファイルを再生できる
- Releaseビルドでも必要なDLLや音声ライブラリが含まれる

## 12. 性能確認

MVPでは厳密な性能目標を別途定める前に、以下の問題がないことを確認する。

- ファイルスキャン中にUIが長時間停止しない
- メタデータ解析中にウィンドウが操作不能にならない
- 楽曲一覧の表示で明らかな遅延がない
- 検索操作が継続的に利用できる
- DBファイルのサイズが不必要に増加しない

代表的な楽曲数のテストデータを用意し、規模が確定した時点で具体的な目標値を追加する。

## 13. テストコードの配置

```text
test/
  unit/
  view_models/
  repositories/
  widgets/

integration_test/
  app_smoke_test.dart
  library_test.dart
  search_test.dart
  metadata_test.dart
  playback_test.dart
```

実際の構成はコード量に応じて調整してよいが、テスト対象とテスト種別が分かる配置を優先する。

## 14. テスト実行結果の報告

作業完了時には、以下を報告する。

- 実行したコマンド
- 成功したテスト
- 失敗したテスト
- 実行できなかったテストと理由
- macOS / Windowsのどちらで確認したか
- 既知の制限や未確認事項

テストを実行していない場合、「動作確認済み」と報告してはならない。
